# 2026-11-19 检索词库 V2.0：设计、迁移与落地

> 回应《检索能力与业务目标不匹配》那份评估。本文做三件事：
> ① 用代码与运行数据核对那 7 条判断；② 补两个被低估的事实；③ 给出 V2.0 的配置结构、主题树、
> 迁移映射与分期落地（**只出设计，未改任何配置文件**）。

## 1. 结论先行

1. 那 7 条判断里，**5 条完全成立、1 条方向对但归因要修正、1 条被低估**（详见 §2）。
2. 被低估的事实：**检索层现在只占每轮候选的约 5%、占入库信号的 3.4%**（§3）。
   所以在没有新后端之前，重构 38 条 query 的杠杆极小；**先接后端，再重构词库**——顺序反了会白干。
3. 被低估的第二件事：`paired_sources` 不是孤例。`retrieval_query`/`retrieval_label` 两个字段
   已经随候选一路写着，但**全仓没有任何消费方**（§5）。V2.0 如果继续加"配置字段"，只会再生产几个死配置。
   **原则：新字段必须同时有读取方和验收方式，否则不进配置。**

## 3. 检索层在整条链路里的真实权重（这是排序依据）

| 环节 | 每轮数量（11-19 实测） | 占比 |
| --- | --- | --- |
| 抓取候选 | 546–594 | 100% |
| ├─ RSS / 页面 / GitHub 等订阅 | 约 519–567 | **≈95%** |
| └─ 检索（38 次调用） | **26–28** | **≈5%** |
| 送模型判定 | 约 245 | — |
| 发帖 | 6–17 | — |
| 自 11-16 起入库信号中检索来源 | **4 条 / 119（3.4%）** | `hn_algolia · a-ai-daily/industry-trend/llm-release/codex-claude-sdk` 各 1 条 |

**含义**：
- 现在把 38 条 query 写到完美，上限也就影响 5% 的候选；
- 反过来，一旦接入通用 Web 搜索（每轮再加几百条），检索会立刻变成**主要发现面**——
  那时候词库的质量才开始决定日报质量。**所以顺序是"后端 → 词库 → 评估"，不是反过来。**

## 4. 前端（后端）能力矩阵：先解决"能不能找到"

### 4.1 原则：**只用免费、免 key 的后端**（付费 API 不纳入方案）

Tavily / Serper / Bing Web Search / Brave Search 一律不接：要 key、要走采购、每次调用有成本。
下面全部是免 key 可跑的，**已于 2026-11-19 17:0x 本机实测**（非公司内网，可达性仍需在生产机复核）。

| 后端 | 类型 | 中文 | 真实原文 URL | 摘要 | 实测条数 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **Bing News RSS** `bing.com/news/search?q=…&format=rss` | 搜索 | ✅ | ✅ `link` 里的 `url=` 参数解码即原文 | ✅ `description` 是正文导语 | 5–14 | **主力发现层**（唯一同时给真实 URL + 摘要的免费后端） |
| **Google News RSS** `news.google.com/rss/search?q=…&hl=zh-CN&gl=CN&ceid=CN:zh-Hans` | 搜索 | ✅✅ | ❌ `link` 是 `news.google.com/rss/articles/CBMi…` 跳转，无法解析 | ❌ 只有标题 | 3–12 | **广度补充**：中文政策/行业覆盖最好；只当线索，不当原文 |
| HN Algolia（现有） | 搜索 | ❌ 中文 query 实测 **0 命中** | ✅ | ❌ 只有讨论链接 | 20 | 保留，只跑英文技术词 |
| arXiv API（现有，关） | 搜索 | — | ✅ | ✅ | 20（会 429） | 只给 research 类 T2 词，间隔 3s |
| GDELT DOC API | 搜索 | 一般 | ✅ | ✅ | 本机 429 | 需要退避 + 低频，作为"重大事件"兜底 |
| 雷峰网 / InfoQ 中文 / 钛媒体 RSS | 订阅 | ✅ | ✅ | ✅ | 19–20 | 建议新增（补中文科技） |
| 36氪 / 机器之心 RSS | 订阅 | ✅ | — | — | **0** | XML 不合规，两家都解析不了，不可用 |
| 百度新闻 RSS / 搜狗 / 财联社 / 北极星 / 中国能源报 / 能源局 RSS / RSSHub 公共实例 | — | — | — | — | 404 / 403 / 非 XML | **不可用**，不要写进方案 |

> 关键结论：**免费方案里，只有 Bing News 能同时给"真实链接 + 摘要 + 时间"，它是不可替代的那一个。**
> Google News 中文召回最好但链接不可回溯，只能做"发现线索"。能源/政策类垂直站基本没有可用 RSS，
> 这部分继续走现有的 listpage 抓取（部委/协会）——不花一分钱，也不用 key。

### 4.2 适配器设计（对应代码改动点）

**`search_bing_news`**（建议 `backend: bing`）
- 请求：`?q=<query>&format=rss&sortby=date&count=30`（实测 `count=30` 实际返回 14 条，够用）
- 解析：`link` 中的 `url=<百分号编码>` → 解码得**真实原文 URL**；`Source: <媒体名>` 作 `source_name`；
  `description` 作 `excerpt`；`pubDate` 作 `published_at`（走现有 `to_cst_iso`）。
- tier：按媒体名映射（新华网/人民日报/央视/部委 → `authority`，其余 `media`），映射表放 `queries.yaml` 的
  `publisher_tiers`，找不到就 `media`。
- 去重：真实 URL 走 [dedup.normalize_url](../01-采集器/collector/dedup.py#L16)，与 RSS 源天然合流。

**`search_gnews`**（建议 `backend: gnews`，只给 T0/T1 的中文政策与产业词）
- 请求：`?q=<query> when:3d&hl=zh-CN&gl=CN&ceid=CN:zh-Hans`（`when:` 实测有效：`when:1d` 返回 3–12 条）
- 标题需去掉尾部 ` - 媒体名`（等于免费的来源标注）；`url` 用 `<source url>` + 标题哈希拼一个占位链接，
  并在 `excerpt` 写明`来源：媒体名（Google News 线索）`，**标记为"未回溯原文"**，
  由 P2 的官方核实步骤决定是否转正。
- **限速**：连续调用必须间隔 ≥2.5s（本轮实测 429 一次、加间隔后连续 4 次全部 200）。

**全局约束**
- 现有 [http_get](../01-采集器/collector/sources/fetchers.py#L24) 是单发、无退避、无 UA，
  接这两个后端前必须补：浏览器 UA + 429/5xx 退避（1s/3s/9s）+ 单轮总调用预算。
- 预算建议：Bing 每轮 ≤20 次（无强制间隔，实测快）、Google 每轮 ≤10 次（2.5s 间隔 ≈ 25s）、
  arXiv ≤2 次。全部加起来每轮 ≤60s，对 4h 一轮完全够。

## 5. V2.0 配置结构：每个字段都要有读取方

| 字段 | 作用 | 现在有读取方吗 | 落地成本 |
| --- | --- | --- | --- |
| `id` / `topic` / `subtopic` | 分类与统计维度 | 部分（`layer` 有读） | 低：`run_queries` 加分组计数 |
| `intent`（theme/product/company/scenario/research） | 检索意图 | ❌ | 低：只用于评估与去重分组，不参与执行 |
| `queries: [{lang, text}]` | 双语检索 | ❌ 现在只认 `query_en` | 中：改 `iter_query_strings`（[queries.py:42-55](../01-采集器/collector/queries.py#L42)） |
| `backends: [hn, gnews, bing, arxiv]` | 按词路由后端 | ❌ 现在"所有 query × 所有启用引擎"（[queries.py:152-153](../01-采集器/collector/queries.py#L152)） | 中：同一处加路由过滤 |
| `priority: T0/T1/T2` | 频率与额度 | ❌ | 中：需配合"轮次调度"（T0 每轮、T2 每天一次） |
| `time_window_hours` / `max_results` | 单条覆盖全局值 | ❌ 现在全局 `limit_per_query=20`、`window_hours=72` | 低：`run_queries` 已收这两个参数，改成按 entry 覆盖即可 |
| `dedup_group` | 组内去重统计 | ❌ | 低：只用于评估口径 |
| `questions` | 关联集团问题 | ✅ 已读 | 无 |
| `paired_sources` | 官方核实映射 | ❌ 死配置 | **高**：要新增"事件→官方源核对"步骤（见 §7） |
| `enabled` | 开关 | ❌ （引擎有，query 没有） | 低 |

**两条硬约束**（避免重演 `paired_sources`）：
1. 任何新字段必须同时改"读取方 + 一个可观测输出"（日志或 `runs.report` 计数），否则不加。
2. `queries.yaml` 必须进 `validate_config`：id 唯一、backend 在注册表内、questions 存在、
   `paired_sources` 的源名在 `sources.yaml` 里存在。**这条是零风险低成本，建议先做。**

## 7. 分期落地（每期都能单独验收）

### P0-a 先补观测（半天，零风险）

- `run_queries` 的 `stats` 增加 **per-query 计数**：`{query_id: {calls, candidates}}`；
  候选上的 `retrieval_query` 已经在（[queries.py:168-171](../01-采集器/collector/queries.py#L168)），
  只需在 `runs.report` 里落一份聚合。
- `validate_config` 增加 queries.yaml 校验（id 唯一 / backend 合法 / questions 存在 / paired_sources 存在）。
- **验收**：`collector status` 能看到"本轮 38 次调用、每次召回几条、哪几条最终入库"。

### P0-b 补后端（决定整个 V2.0 是否值得做）

- 本机已完成首轮实测（见 §4.1）：**Bing News RSS + Google News RSS 可用**，GDELT 需退避、RSSHub 公共实例/百度新闻/Reddit 不可用；
- 在生产机复测这两条 URL 是否可达（`http_get` 无代理，失败模式同 Hugging Face）；
- 在 [queries.py:133](../01-采集器/collector/queries.py#L133) 的 `SEARCHERS` 注册 `bing_news`/`gnews` 两个 `kind`，
  先给 [http_get](../01-采集器/collector/sources/fetchers.py#L24) 补浏览器 UA + 429/5xx 退避；
- **验收**：同一条中文政策类 query，Bing 召回 ≥8 条且 `url` 为真实原文域名；Google 召回 ≥5 条；
  连续 20 次调用不出现未处理异常。

### P1 词库 V2.0（后端就绪后一次性迁移）

- 按 §6 主题树生成 `queries-v2.yaml`，**保留 v1 的 id 映射表**（便于回滚与对比）；
- `run_queries` 支持按 entry 路由 `backends`、覆盖 `max_results`/`time_window_hours`、双语 `queries`；
- **验收**：连续 3 轮，T0 词每轮都有结果、T2 词每天一次；每主题入库 ≥1 条（否则说明词或后端有问题）。

### P2 官方核实（`paired_sources` 复活）

- 最小实现：对 `relevance≥2` 且首发为 media 的信号，用 `paired_sources` 里的官方源 + 该事件实体做一次
  "官方源内检索"（RSS/站点搜索都行），命中则把官方 URL 追加进 `sources`（`cred` 自动升 yellow/green）；
  未命中则在 `us`/摘要里标注"仅单一来源"。
- **验收**：media 类信号里，官方二次核实的命中率作为固定指标进 `runs.report`。

### P3 评估闭环

看板最小字段：`query_id / calls / raw / dedup / kept / posted / below_min_relevance / official_verified`，
周维度看"哪条词边际价值为 0"。判废标准建议：连续 2 周 `kept=0` 且 `candidates>0` → 降级或改写。

## 8. 需要你拍板的两件事

**已定**：只用免费、免 key 后端（2026-11-19 决策）。付费 API 不进入方案，P0-b 的候选范围收敛为
**Bing News RSS（主力）+ Google News RSS（广度补充）+ HN（英文技术）+ arXiv（T2 研究）**。

1. **T0/T1/T2 的执行频率**：T0 每轮（4 次/天）、T1 每轮、T2 每天一次 —— 还是全部每轮？
   （影响最大的是 Google 的 2.5s 限速：全量每轮会让每轮检索耗时从 ~60s 升到 3–4 分钟）
2. **Google News 线索能否入库**：它的链接无法回溯原文（`news.google.com/rss/articles/CBMi…`）。
   两种做法——
   - 只做"漏报检查"：不进信号库、不出现在首页，只写进 `runs.report` 的"线索"条目，人工看一眼；
   - 直接入库但标注"Google News 线索 / 未回溯原文"，等 P2 官方核实后再转正。
   我倾向后者（对中文政策覆盖帮助最大），但需要你确认可接受"首页出现无法点回原文的条目"。

#### C2 的历史漏洞（2026-11-16 已修）

旧代码写的是：

```python
if c.published_at and datetime.fromisoformat(c.published_at) < window:
```

`published_at` 为 `None` 时整段判断被 `and` 短路——**零日期条目 100% 绕过 72 小时窗口**。
实际后果：一条 2026-10-30 的网信办公告（超窗 17 天）被当成新信号发布（话题 755），
一条 11-05 的中国电力报同样漏过（话题 746）。这类条目全部来自 `manual_pages`
（政策官网、GitHub、企业博客），它们天然没有 `pubDate`。

修复分三层：

1. `pubdate.py` 从 URL 抠日期戳（`/2026-10/30/`、`/202611/t20261105_` 等），
   补进 `published_at`；过滤版本号、非法日期、未来日期、域名里的数字。
2. 仍提不出日期的按 `round.undated_policy` 处理，默认 `drop`（无法证明新鲜就不收），
   可用 `keep` 回退，两者都单独计数（`undated_dropped` / `undated_kept`）。
3. `tagger.py` 把模型给的 `event_date` 与信源日期对账，偏差超 1 天即认定模型编造，
   改以信源日期为准；模型没给 `event_date` 时用信源日期补上。

## 四、可信度分级（实测，修正之前的错误认知）

```python
authority 存在                        → green  🟢
official + 独立源(media/research)      → green  🟢
official 单源                          → yellow 🟡
两个不同 host                          → yellow 🟡
其他（单一 media/research/community）  → red    🔴
```

实测验证：

| 场景 | 结果 |
|---|---|
| 单条 media（IT之家） | 🔴 red |
| 单条 official（OpenAI） | 🟡 yellow |
| 单条 authority（能源局） | 🟢 green |
| official + media 双 host | 🟢 green |
| 两条 media 不同 host | 🟡 yellow |

**修正**：不是"cred 永远全红"。之前 5 条信号全红，是因为来源恰好都是单条 media/research。新加的 GWEC、WindEurope、BNEF、国家能源局都是 `authority`/`official` 层，会产出 🟢/🟡。

## 五、结构性缺口（按严重度排序）

### 🔴 高：两个库重复抓 23 个域名

同一批 URL 被采集器和日报各处理一次。采集器已经加工过的内容，日报的 `fetch_sources` 兜底路径还会再抓一次。**这是整合没完成的核心标志。**

### 🔴 高：A/B 层检索词是死的

11 组 A 层 + 7 条 B 层检索词只写在 Markdown 里，没有任何代码读取。采集器不做搜索，只做订阅。这意味着：
- "能源全产业链 AI"、"风电竞品 AI"这些检索词**从未被自动执行**
- 只能靠执行 Agent 手动遵守

### 🟡 中：竞对官网全部抓不到

Vestas、SGRE、明阳、远景、三一、电气风电——全 SPA 渲染 + 无 RSS。目前靠 Windpower Monthly / reNews 等行业媒体间接覆盖（47 条/轮），但：
- 滞后 12-24 小时
- 小消息会漏

### 🟡 中：三个能源媒体只在日报侧

中国电力报、新华网能源、中国能源网——采集器没有。

### 🟢 低：6 个 `page` 型源靠 Agent 人工核查

日报 `sources.json` 里 20 个 `page` 型源，脚本不抓，要执行 Agent 逐个打开。这是设计选择，不是缺陷，但会让人工成本随源增长而线性上升。

## 八、中文检索词问题（2026-11-16 修订）

### 8.1 问题

`queries.yaml` 1.0.0 版里每组检索词都有 `zh` 和 `en` 两份，执行器**两种语言各发一次**。
但检索后端是 HN Algolia（英文站），实测：

| 检索词 | HN 返回 |
|---|---|
| `大模型 发布 更新 开源` | **0 条** |
| `人工智能+ 能源 试点 应用 案例` | **0 条** |
| `AI energy pilot application` | 3 条 |

等于每轮白跑一半请求。

### 8.2 改法：英文检索 + 中文展示

```yaml
# 改前
zh: "大模型 发布 更新 开源"     # 也拿去搜，0 结果
en: "LLM release update open source"

# 改后
label_zh: "大模型版本发布"       # 只作回显标签，不参与检索
query_en: ["LLM release update open source", "large language model new release"]
```

链路变成：

```
英文检索词 → HN 返回英文标题 → tagger 翻成中文 title + 中文 summary → 论坛发中文帖
```

翻译由 `tagger` 完成——它本来就要求输出中文 `title`（15–60 字）和中文 `summary`（≤120 字），
不需要额外的翻译步骤。

### 8.3 顺带修掉的三个真问题

**① HN 无时间过滤，旧闻占绝对多数**

实测全量检索 340 条，最早 **2008-06-10**——HN Algolia 默认按相关性排序，旧文排前面。
加 `numericFilters=created_at_i>T` 后，72 小时窗口只返回 20 条。

**② 模型用 `[]` 代替 `{keep:false}`**

对「明显不值得保留」的条目（未经证实的阴谋论、Show HN 自建项目），模型会整批返回 `[]`，
而不是按格式返回 keep=false 的对象。原来被当成「模型漏掉了这一条」丢进 pending。

实测：同一条重复 5 次稳定返回 `[]`，纯文本追问明确答「不值得」——**判定意图是对的，只是格式不合规**。
现在把 `[]` 解释为「整批都不保留」，真错误从 7 条降到 **0 条**。

**③ 同标题进同一批导致整批作废**

批次内出现相同标题时，模型更容易整批返回 `[]`。现在检测到重复标题就拆成单条重送，保住其余有效条目。

> 注：不要在上层（pipeline 的 URL 去重）加标题去重——那会破坏「两家媒体互证合并为一条」的事件合并逻辑
> （`test_round_end_to_end` 会失败）。

### 8.4 修订后的实测结果

```
检索调用    38 次成功 / 0 失败
候选        20 条原始 → 19 条去重
打标        1 条保留 / 18 条判不保留 / 0 条真错误
翻译        「Show HN: Port of Context – Token efficient MCP context layer」
         → 「HN展示Port of Context：高效MCP上下文层工具」
```

保留率低（1/19）是**正常的**：HN 72 小时内的 AI 相关帖多是 Show HN 自建项目和阴谋论，
模型判无关是对的。真正的信号密度要看 `a-wind-peers`、`a-energy-chain` 这些专业检索组。

### 8.5 仍然存在的中文缺口

英文检索 + 中文翻译解决了**海外内容的中文化**，但解决不了**中文内容的发现**：

- 中文源（量子位、机器之心、IT之家、中国电力报、新华网能源）走的是**订阅**，不是检索
- 中文检索需要中文搜索后端（百度/搜狗/微信搜索），当前全部不可用或需 key
- 因此 `queries.yaml` 里 `a-energy-chain`、`a-energy-policy` 这些组，`paired_sources` 标注的
  中文官方源才是中文线索的真正来源——但**配对逻辑还没实现**（见 7.5）

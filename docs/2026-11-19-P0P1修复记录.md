## 3. P1：来源白名单补判（方案 C 最小版）

### 为什么

`keep` 是流水线里唯一的实质闸门，判据却是「与集团问题是否相关」。
官方一手发布通常只有「发布了什么」，没有解读，最先被判掉：
2026-11-19 实测 OpenAI / Anthropic / DeepMind 三组官方源 20 条候选只留下 3 条，
而 97 条信号里 30% 来自 IT之家这类二手媒体 —— 一手信息在入口处就被掐掉了。

### 怎么做

1. 第一遍照常打标签（`tag_candidates`）。
2. 被判 `keep=false` **且信源在人工白名单内**的候选，拼成一小批再问一次
   （[pipeline.py:200](../01-采集器/collector/pipeline.py#L200)），
   这次带上补判提示词 [tagger.py:51](../01-采集器/collector/tagger.py#L51)：
   「本批是来源白名单补判，默认 keep=true，只补字段，只有招聘/活动预告/纯营销软文才给 false」。
3. 补判结果 `keep=true` 的替换原结果，计数进 `RoundReport.keep_bypassed`，日志打一行
   「白名单补判：N 条被 keep=false 的一手来源重新保留」。
4. 补判本身抛错只记 warning，不影响整轮。

白名单在 [settings.yaml:88](../01-采集器/config/settings.yaml#L88)，26 个信源，分三类：
模型厂商官方发布、监管与政策原文（网信办/能源局/发改委/工信部）、
行业机构与整机厂官方（GWEC / WindEurope / BNEF / GE Vernova / Nordex / 东方电气 / 新华网能源）。
名字必须与 [sources.yaml](../01-采集器/config/sources.yaml) 的 `name` 原文一致（含空格与斜杠）；
有校验脚本口径，可用 `load_config()` 交叉核对。

### 安全边界

- **只放宽 keep，不放宽 relevance**。救回来的条目 relevance 仍由模型照常给，
  `round.min_relevance_to_post: 2` 这道门槛不变 —— 只是行业背景（relevance=1）的照样不发帖，
  只会落进 `rep.below_min_relevance` 计数。
- 名单是人工维护的「这是不是一手来源」判断，模型不再有自由裁量权；
  想让某个源回到旧行为，从名单里删掉它即可。
- 只补判「第一遍判定成功但 keep=false」的条目；模型调用失败（`error`）的条目不补判，
  仍是下一轮重抓。
- `keep_bypass.enabled: false` 一键回退。

## 6. 两个需要盯着的点

1. **底座帖容量到顶**：36 条雷达就 27,969 字符（预算 28,000），`max_items: 40` 实际上只能放 36 条。
   P1 让一手条目变多之后 radar 只会更挤，`write_feed` 的二分收缩会一直触发（日志有 WARNING，不是错误）。
   下一步要么压 summary 上限，要么把 `feed.window_hours` 从 72 收到 48。
2. **补判的条数要有人看**：`collector status` 已经会打印「白名单补判 N 条」。
   如果哪天 N 很大而首页肉眼没变化，多半是补判回来的条目 relevance 都是 1（只到行业背景），
   属于白名单开得过宽，该收名单而不是关开关。

# 2026-11-19 事故复盘：08:00 采集卡死 43 分钟，首页停更

## 一句话

08:00 那一轮卡在「论坛限速 → 睡眠重试」里 43 分钟没退出，单实例锁被长期占用，
首页停在 11-18 的数据；如果没人管，12:00 和 16:00 两轮也会因为「上一轮仍在运行」被跳过。
已修三处根因，并加了本轮硬超时兜底。手工补跑一轮后首页已恢复正常。

## 现象（08:43 现场）

| 观察 | 值 |
|---|---|
| 进程 | `collector run --on-load-check`，08:01:48 启动，已跑 41 分 47 秒 |
| CPU | 0.0%（累计仅 6.29 秒） |
| 网络连接 | `lsof -a -i` 为空——没有任何打开的 socket |
| `sample` | 主线程停在 `time_sleep → nanosleep` |
| runs 表 | 该轮 `report` 为空（没走到 finally） |
| 日志 | 只有一行「按计划时刻触发，直接采集」，之后什么都没有 |
| 底座帖 | 最后写入 2026-11-18T18:29，即首页停在前一天 |

## 根因：三层叠加

### 1）一轮里发了 55 次「补发帖人」请求

论坛 `/c/{id}/l/latest.json` 返回的 topic **不含 posters 字段**。
实测（8 个可见分类）：55 条帖子，55 条 `who` 都是空的。
`scan_forum` 末尾对每一条都调一次 `topic()`——那是完整的帖子 JSON 请求。
**55 次连续请求**，而论坛 admin API key 有每分钟次数上限。

### 2）撞上限额之后，睡得比该睡的久得多

429 的响应头：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 4
Discourse-Rate-Limit-Error-Code: admin_api_key_rate_limit
```

旧 `_req`：按 `Retry-After` 睡眠，最多重试两次，单次上限 120 秒。
限额被打满后，**每个**请求都要睡；一轮几十个请求累加，就是几十分钟。
（08:44 实测 `Retry-After` 是 4 秒，限速窗口快过去了；打满时给的是几十秒级。）

### 3）没有「本轮必须有始有终」

`run_round` 只有 `try/finally` 落库，没有任何时间上限。
卡住 = 进程不退出 = `state/run.lock` 一直被 flock 占着，
`_acquire_run_lock` 拿不到锁的后续轮次会打印「上一轮采集仍在运行，本轮跳过」并**以退出码 0 结束**——
launchd 看来一切正常，日志里连一句失败都没有。这比报错更糟。

### 附带问题：模型接口超时把人工队列灌满了

当天 `pending` 表 65 条，其中 48 条是
`模型调用失败：HTTPConnectionPool(host='10.111.32.151', port=3001): Read timed out. (read timeout=45)`、
8 条是模型回了坏 JSON。这些条目下一轮会被重新抓到、重新判定，
记进「待人工」纯属噪声——而且没有任何消费入口，永远不会有人处理。

## 修了什么

| 文件 | 改动 | 目的 |
|---|---|---|
| `collector/discourse.py` | 新增 `_pace()`：相邻请求最小间隔 **1.0 秒**、每分钟上限 **40 次**；429 只重试 **一次**、单次等待压到 **≤10 秒**；统计 `requests_made` / `rate_limited` | 不再撞限额；即使撞上，单个请求最多损失 10 秒而不是 240 秒 |
| `collector/community.py` | `scan_forum(with_authors=False)`；新增 `resolve_authors()` | 扫描阶段 0 次 `topic()`，只为最终展示的那几条补作者（55 → 5） |
| `collector/pipeline.py` | `update_feed` 先 `pick_community` 再补作者；本轮看门狗；①–⑦ 分阶段日志；模型故障记 `model_failed` 不进 pending；报告新增 `forum_requests` / `rate_limited` / `model_failed` | 少发请求、卡住能看出卡在哪、噪声不入人工队列 |
| `collector/watchdog.py`（新） | `RoundTimeout` + `arm()/clear()`，基于 `signal.setitimer` | 本轮硬超时，超了就走 finally（落库、告警、放锁） |
| `config/settings.yaml` | `discourse.min_request_interval: 1.0`、`discourse.max_requests_per_minute: 40`、`round.max_seconds: 1200` | 上面三项的配置口 |
| `collector/__main__.py` | `status` 每轮多显示「论坛限速 429×N / 论坛请求 N 次 / 模型故障 N 条」 | 下次出问题不用再靠 `sample` 猜 |
| `tests/test_resilience.py`（新） | 8 条回归测试 | 限速、429 上限、看门狗、社区补作者、模型故障入账 |

一个坑：`RoundTimeout` 必须继承 **`BaseException`**。第一版继承 `Exception`，
结果超时被「单个信源失败不影响其余」的 `except Exception` 吞掉，整轮照样跑完，看门狗等于白设。

## 顺手清理

`pending` 表 65 条里，62 条是模型侧噪声（超时 / 坏 JSON / 模型漏条）。
已归档到 `logs/pending-archive-20261119.json` 后删除，只留下 3 条「标题疑似重复」。
现在 `status` 显示的「待人工」重新有了意义。

## 仍然存在的风险

1. **模型接口偶发超时**：今天一轮里 48 条没能判定。现在不会再污染 pending，但那批信号当轮就没上首页，要等下一轮重新抓到（72 小时窗口内会）。
2. **两个信源长期失败**：Hugging Face（连不上）、机器之心（RSS XML 本身损坏，连续 14 轮）。前者按你的要求保留，后者其实已经没救——要不要禁用，你定。
3. **看门狗依赖 SIGALRM**，只在主线程有效。launchd 与手工 `python -m collector run` 都是主线程，够用；将来若改成线程池并发要重新设计。
4. **被看门狗中止的那一轮不发帖、不刷底座帖**，靠下一轮补。因为 08/12/16 之间隔 4 小时，20 分钟上限不会造成连环跳过。

# 2026-11-19 一手源为何缺席：采集器「二手媒体为主」的链路分析

> **一句话**：不是采不到一手源，而是**链路上没有任何一个环节认「一手」这个属性**——
> 入口按「谁发得勤」分配额度、keep 按「与集团 9 个问题是否相关」判、排序只看 relevance / cred / 时间、
> 合并与署名先到先得。二手媒体靠产量和文体在每一关都能赢一手源。

- 分析范围：`01-采集器` 全链路（配置 / 抓取 / 去重 / keep 判定 / 排序 / 渲染 / 检索）
- 分析方式：**只读**。代码与配置未改；`state/index.sqlite` 复制到 /tmp 后用仓库自带
  `collector.render` / `collector.focus` 做离线回放；抓取样例为**本机实测**，可能与生产机网络有差异，单独标注。
- 数据时点：2026-11-19 16:34（16:00 那一轮已跑完：发帖 6 条）

## 3. 五道关口，逐一看它怎么偏

### 3.1 入口：一手源里有一批「结构性永远 0 条」

1. **`kind: page` 的官方页面根本不进候选池。**
   [pipeline.py:124](../01-采集器/collector/pipeline.py#L124) 建源时直接
   `x.get("kind") != "page"` 过滤掉，[fetchers.py:230-236](../01-采集器/collector/sources/fetchers.py#L230)
   里 `MANUAL_KINDS` 再次 `return []`。而 `enabled: true` 的 page 源有 **11 个**：
   Anthropic `/news`、Meta AI、Microsoft AI、xAI、Qwen、豆包、智谱、Kimi、MiniMax、百度、混元。
   **它们每轮固定贡献 0 条**——Anthropic 官方新闻从来没进过池子（日志里的
   `"Anthropic / Claude": 20` 其实是 Claude Code 的 GitHub releases）。
2. **IT之家拿到两份独立额度。** 两个源同一个 URL，每轮对同一份数据发两次 GET，
   两套关键词各自过 30 条上限（[fetchers.py:273](../01-采集器/collector/sources/fetchers.py#L273)），
   单站单轮 27+16≈43 条候选。IT之家一天几十更，几乎条条在 72h 内。
3. **每源 30 条上限在「窗口判断之前」截断。** [fetchers.py:273](../01-采集器/collector/sources/fetchers.py#L273)
   先 `out[:30]`，再由 [pipeline.py:169-184](../01-采集器/collector/pipeline.py#L169) 判 72h 窗口。
   高产站的额度 100% 用得掉，低产官方用不满：本机实测 OpenAI news RSS 共 166 条、
   最近 30 条里**窗内 17 条**；DeepMind blog 最近 30 条里**窗内 2 条**；
   blog.google AI **3 条**；DeepSeek 更新日志 **0 条**（页面最新日期 2026-11-13，超窗）。
4. **观测口径把一手源的产量藏起来了。**
   [pipeline.py:134](../01-采集器/collector/pipeline.py#L134) `rep.fetched[src["name"]] = len(got)`
   用**源名**做 key，同名源互相覆盖：`OpenAI / Codex`（RSS + releases）、
   `Anthropic / Claude`（page + releases）、`Google DeepMind / Gemini`（两个 RSS + releases）。
   于是报表里 `"OpenAI / Codex": 4` 实际是 Codex releases 的数字，
   **OpenAI RSS 的 17~18 条在报表里消失**；失败与成功也会互相掩盖。这一条不修，
   后面所有"官方没产出"的判断都不可信。
5. **单源没有重试 / 退避。** [fetchers.py:24-31](../01-采集器/collector/sources/fetchers.py#L24)
   单次 `requests.get(timeout=20)` + `raise_for_status()`，失败只记 `failed_sources`。
   实测 Hugging Face 连续 9 轮连接超时、DeepMind `blog.google` 偶发 SSL EOF、机器之心 XML 坏 14 轮后被停用。

### 3.2 门禁：keep 的判据天生不适合「官方只发布、不解读」

- keep 提示词原文（[tagger.py:30](../01-采集器/collector/tagger.py#L30)）：
  > `keep：这条是否值得进情报站。与上述问题都无关、纯营销软文、旧闻重发、招聘、活动预告，keep=false`

  「上述问题」= [questions.yaml](../01-采集器/config/questions.yaml) 的 9 个集团问题。
  模型收到的每条只有 `source/title/excerpt/published_at`
  （[tagger.py:112-118](../01-采集器/collector/tagger.py#L112)）——**看不到 tier，提示词里也没有"一手优先"条款**。
- 由此形成结构性劣势：二手稿自带「这对谁意味着什么」的解读，天然命中 Q03/Q04；
  官方 release note 只陈述"发了什么"，最先被判掉。实测每轮 keep=false 率 **92%~97%**。
- 已上线的 P1 白名单补判（[pipeline.py:204-225](../01-采集器/collector/pipeline.py#L204)，
  开关与 26 个名单源在 [settings.yaml:88-119](../01-采集器/config/settings.yaml#L88)）每轮救回
  **4~16 条**——这本身就是"官方正在被误杀"的直接证据。
- 但补判**只放宽 keep、不放宽 relevance**（[settings.yaml:72](../01-采集器/config/settings.yaml#L72)
  + [pipeline.py:286-290](../01-采集器/collector/pipeline.py#L286)）。救回来的条目若 relevance=1，
  照样进不了发帖队列，而且这一层的损耗**混在 `below_min_relevance` 里，无法归因**。
- relevance 是第二个杀手：全库 official 拿 3 分 **0/14**，媒体 4 条。3 分的定义是
  "直接影响集团业务或决策"（[tagger.py:34](../01-采集器/collector/tagger.py#L34)），
  语义上要求有人替读者完成"对我意味着什么"的翻译——这正是媒体的文体。
- 连带后果：公开版门槛 `public_min_relevance: 3`（[settings.yaml:14](../01-采集器/config/settings.yaml#L14)）
  意味着**一手发布（rel=2）永远发不出公开版**，而 rel=3 的二手稿可以。

### 3.3 排序：tier 里没有「一手」

- `_brief_rank`（[render.py:499-526](../01-采集器/collector/render.py#L499)）：
  `rel≥3 → tier0`（全库 5%，官方 0/14，这一档基本空转）；
  `domain∈{能源AI,政策合规}` 或命中 Q02/Q05 `→ tier1`——**二手媒体的政策解读同样进 tier1**；
  其余 tier2。整条公式里**没有任何 `sources[0].tier` 判断**。
- `radar_rank`（[render.py:351-358](../01-采集器/collector/render.py#L351)）：
  日分组 → `3×cred + 2×rel/3` → 精确时间。同样不含来源层级。
  媒体一天几十条在刷新"最新"，官方一周几条，雷达自然被前者填满。
- 同源限额（按 host 分桶，[render.py:534-549](../01-采集器/collector/render.py#L534)）**已落地且有效**，
  但只作用于 01 / 02 / 主线 / 今日值得看；**03 雷达走 `sigs[:max_items]`，没有任何 per-host 限额**
  （[pipeline.py:545-546](../01-采集器/collector/pipeline.py#L545)）。
  而且 `_diverse` 有"凑不满就放宽到不限源"的兜底轮（[render.py:577-585](../01-采集器/collector/render.py#L577)）。
- 时效降级（[render.py:484-526](../01-采集器/collector/render.py#L484)）会把两天前的官方 rel=3 直接压到 tier5，
  实测国家网信办两条 rel=3 / green 在 11-16 就已沉底——**相关度 3 也救不回两天前的官方稿**。

### 3.4 合并与署名：先到的那条永远是「门面」

- 同一事件合并只做 `existing.sources.append(ref)`（[pipeline.py:262-271](../01-采集器/collector/pipeline.py#L262)）：
  标题、摘要、domain 全部保留最先入库那条；首页 `from`/`url` 读 `sources[0]`
  （[render.py:379](../01-采集器/collector/render.py#L379)、[:531](../01-采集器/collector/render.py#L531)）。
  **没有"官方原文覆盖二手转述"的规则。**
- 合并还要求 `event_key` 完全相同，而 event_key 是模型按内容生成、带日期
  （[tagger.py:38](../01-采集器/collector/tagger.py#L38)）。全库 **119 条里只有 1 条是多源**——
  同一件事官方发一遍、媒体转一遍，通常不会合并。
- 标题指纹去重是 0.75 阈值（[dedup.py:130-139](../01-采集器/collector/dedup.py#L130)），
  只在中文标题之间有效。今天的 "谷歌推出 Gemini 4 Neon 模型"（IT之家）与
  "Google DeepMind发布Gemini 4 Neon模型"（官方）跨语种认不出，**两条都发了**。
- 二手稿不可回溯：实测抓了 3 篇 IT之家原文，正文里没有任何指向 openai.com / blog.google 的外链，
  系统即使想"顺着二手找一手"也没有入口。
- 焦点长文理论上"一手优先"（[focus.py:43-44](../01-采集器/collector/focus.py#L43)、
  [:268-276](../01-采集器/collector/focus.py#L268)），但真正的第一关键字是"站点能不能抓到正文"，
  且正文 <200 字 / 凑不出 2 条可逐字校验事实的短小官方发布会被直接跳过
  （[settings.yaml:135-138](../01-采集器/config/settings.yaml#L135)）；抓成功还会把抓到的来源
  提到 `sources[0]`（[focus.py:418-424](../01-采集器/collector/focus.py#L418)），反过来改写首页署名。

### 3.5 检索层不背这个锅，但也没帮上忙

- [queries.yaml:33-50](../01-采集器/config/queries.yaml#L33) 只启用了 HN Algolia（英文社区），
  没有通用 Web 搜索；arXiv 检索默认关闭。**IT之家 / 量子位完全不来自检索**。
- 每轮检索产出候选仅 26~28 条，自 11-16 起入库 5 条。
- `paired_sources`（"发现靠检索、核实靠官方源"）是死配置：全仓没有任何代码读取它。

## 4. 「没有第一时间采用一手源」是怎么发生的（时间线）

```
T+0h      事件发生
T+0~2h    IT之家 发稿 → 下一轮抓取（每 4h 一轮）就进池
          官方原文：等 RSS 更新；若是 kind: page / 超 72h / 抓取失败 → 压根进不来
T+4h      keep 判定：二手有解读 → keep=true；官方只有"发布了什么" → keep=false（或 relevance=1）
          被丢掉的条目不落库、不重试，下轮还会因 URL 已在 url_alias 里被当重复
T+4h~     即使两条都进池：没有"同事件一手优先"规则，
          标题/摘要/署名/焦点正文都按"先到 + 抓得到"决定
```

结果不是"二手补充一手"，而是**二手替代一手**。

## 7. 建议（本次未改代码，按性价比排序）

### P0：先把"看不见"修掉，否则调参靠猜

1. **`fetched` / `failed_sources` / source_health 按源 id 分键**（[pipeline.py:134](../01-采集器/collector/pipeline.py#L134)、
   [:138](../01-采集器/collector/pipeline.py#L138)、[store.py:109](../01-采集器/collector/store.py#L109)）。
   预期：能第一次看清 OpenAI RSS / DeepMind RSS 到底产出多少、失败是谁失败。
2. **IT之家两源共用同一 URL，合并成一个源或共享一次抓取缓存**。
   预期：单站候选量减半，且不再出现"同一份数据两套关键词各自占满额度"。
3. **把 11 个 `kind: page` 官方源改成可抓形态**（RSS / JSON API / sitemap / listpage）。
   预期：官方新闻首次进入候选池；收益最大但也最费工，可按厂商逐个上。

### P1：判据层加"一手"维度

4. **把 `source_tier` 传给模型**（[tagger.py:112-118](../01-采集器/collector/tagger.py#L112)），
   并在 keep 提示词里写明"官方一手发布即便无解读也保留，交给 relevance 分层"。
5. **一手源 relevance 给底分**（例如 official/authority 默认不低于 2），
   让"有没有解读"不再决定"进不进得来"，只决定"排第几"。
6. **补判后被 relevance 挡下的条数单独计数**（现在混在 `below_min_relevance`），
   否则永远说不清"白名单到底救回了多少"。

### P2：排序与合并

7. **`_brief_rank` / `radar_rank` 加入 source tier 权重**。注意这是"一手 vs 时效"的取舍：
   建议在同一档内先比 tier，再比 cred 与时间，而不是把 tier 提到第一关键字（会重蹈
   "旧的重磅永远霸榜"的覆辙，见 [render.py:464-483](../01-采集器/collector/render.py#L464)）。
8. **同事件合并时按 tier 优选标题 / 摘要 / `sources[0]`**，让一手原文成为署名而不是附注。
9. **跨语种同事件识别**：IT之家正文无外链，URL 归并走不通，只能用"实体 + 日期 + 数字"做二次归并；
   否则同一件事永远两条。
10. **03 雷达加 per-host 限额**（可以比 01 宽松，例如每站 ≤2），否则首页修好了、雷达还是媒体墙。

净结果：**8 个 URL 里 3 个接入（#3/#4 同页、#6），5 个登记为不可抓并写明原因。**

未实跑的 5 个不是「忘了配」，而是三条硬事实：
- openai.com 全站 HTML 被 Cloudflare 挡（只有 RSS 端点放行）——**换 UA 无用，实测两种都 403**；
- claude.com 的社区页是 RSC 渲染，静态 HTML 里没有条目；
- 课程目录没有日期，按现有 `undated_policy: drop` 必然全丢。

### 为了让 #4/#6 能抓，顺手改了两处

1. `fetch_listpage` 支持 `link: self`（卡片本身就是 `<a>`）与 `selectors.title`
   （卡片链接文本混着「Article / 日期 / 标题 / 产品标签」，直接取全文标题会脏）。
2. `to_cst_iso` 支持英文月名（`Nov 30, 2026`）。原来只认 ISO、中文年月日、邮件日期三种，
   两家新源整页都会变成「无日期」被丢。测试见 `tests/test_vendor_listpages.py`（7 例）。

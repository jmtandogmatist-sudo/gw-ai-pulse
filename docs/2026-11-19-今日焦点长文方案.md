# 【今日焦点】单独成篇：可行性方案（2026-11-19，先不动代码）

> 目标：02「今日焦点」不再是一句话摘要，而是像参考站 `ai-pulse-lab.com` 那样
> 一篇有导语、有分节、有可核对关键事实的短文；首页 02 只做入口（标题 + 导语 + 要点 + 阅读全文）。
> 本文只给方案与取舍，不改代码。

## 1. 现状（为什么今天是「一句话」）

| 环节 | 现状 | 后果 |
| --- | --- | --- |
| 焦点选材 | `lead_item()` 直接取 01 简报的第一条（同一次 `_top_picks`） | 焦点没有独立选材标准，只是「简报的第 1 条」 |
| 焦点素材 | 只有 RSS/列表页的 `excerpt`（实测 105 字）+ 模型写的 `summary`（≤320 字） | 没有正文素材，模型无从展开 |
| 焦点落点 | 只是 632 底座帖 JSON 里的 `lead` 对象，没有独立话题 | 读者点开是原文外链，站内没有可讨论的长文 |
| 前端渲染 | `ap-lead` 只渲染 `title` / `summary` 一段 / `us` 一句 / 来源 chip；`LIMITS.summary = 320` | 结构上就不可能出现第二段 |
| 底座帖预算 | 正文已 27,969 / 28,000 字符 | **长文绝对不能塞进 632**，只能放摘要 + 入口链接 |

结论：一句话不是「写得太短」，而是**没有素材、没有结构、没有落点**三件事叠加。

## 2. 关键设计判断：焦点不是新实体，是同一条信号的另一套渲染

推荐做法：**焦点信号在发帖时就生成「长文正文」，其余信号仍走标准模板**。

- 不新增话题：焦点话题就是这条信号的话题（`external_id` 幂等机制不变），
  03 信号雷达里它照样出现，`topic_url` 指向同一篇 —— 不会出现「焦点一篇、雷达又一篇」。
- 02 焦点 = 该话题的入口卡（标题 + 导语 + 3 条要点 + 「阅读全文 →」+ 对金风一句）。
- 只要 `focus.enabled: false` 或长文校验不通过，就退回今天的标准模板 + 一句话 summary（行为不变）。

好处：不新建分类、不动权限、不动发帖节奏、不破坏幂等；坏处：这条信号的正文不再是标准四段模板，
需要保证「关键事实 + 来源」信息不丢（见 §3.4 的折叠块）。

## 3. 流水线改动（V1，5 个新步骤，都在发帖之前）

```
抓取 → 去重初筛 → 打标签(keep/relevance) → 白名单补判
        ↓ 新增：焦点选题 focus_pick
  焦点正文抽取 focus_fetch（单条，抓原页正文）
        ↓ 事实抽取 focus_claims（LLM #1，输出带引文的 JSON）
        ↓ 引文校验 focus_verify（纯代码，逐条溯源）
        ↓ 长文成稿 focus_write（LLM #2，只允许用已校验事实）
  → 发帖（焦点话题用长文模板）→ 写 632（lead 只放摘要+入口）
```

### 3.1 焦点选题（`focus_pick`）

一天一篇，08:00 定稿；12:00 / 16:00 只允许「同一事件补充信息」，不换题（避免一天三篇同题）。
候选必须同时满足：

1. 一手来源（`keep_bypass.sources` 名单内）或 ≥2 个不同 host 互证；
2. `relevance ≥ 2`（若当天有 3 就用 3）；
3. 事件在 24 小时内；
4. 该 `event_key` 近 7 天没做过焦点（查 `state` 表）；
5. 正文抽取成功且「可核对事实」≥4 条（不满足就顺位下一条，最多试 3 条）。

焦点一旦选定，**不再出现在 01 简报里**（01 取除焦点外的 3 条），避免同一页两处重复。

### 3.2 正文抽取（`focus_fetch`）

- 只针对 1 条 URL，用已有依赖（`requests` + `bs4`）做启发式抽取：去掉 script/style/nav/footer，
  取 `p/li/h2/h3` 文本，过滤 <20 字的段落，上限 8,000 字。
  **不新增依赖**：venv 里没有 lxml / trafilatura，内网 pip 不一定可达，bs4 足够。
- 同事件多源（`event_key` 合并过的 `sources`）各抽一份，互证数字用。
- 抓取失败（企业网对外站点确实会超时，见 Hugging Face 连续 9 轮失败）→ 该候选降级跳过，换下一条；
  全失败则今天不出焦点，退回一句话（并在 round report 记 `focus_skipped`）。

### 3.3 事实抽取 + 引文校验（核心质检）

LLM #1 的输入只有正文（+ 标题），输出严格 JSON：

```json
{"claims": [{"text": "Neon 输入价 3 美元/百万 token", "quote": "Pricing is $3 per million input tokens", "source": "https://…"}],
 "numbers": [{"value": "3", "unit": "美元/百万token", "what": "输入定价"}],
 "what_changed": "一句话说清这条为什么值得展开"}
```

`focus_verify` 用纯代码校验（不靠模型自觉）：

- 每条 `quote` 必须在抽取正文里**逐字出现**（归一化空白与全半角后）；
- 每个数字必须在正文出现同形或同值；
- 校验失败的 claim 直接删除；剩 <4 条 → 降级（见 3.5）。

这一步是「不能是一句话」和「不能编」的唯一调和点。参考站也是这么做的：它把
`Claim + Quotation + isBasedOn` 写进 JSON-LD，等于给每条事实挂了可核对的引文。

### 3.4 长文成稿（`focus_write`）

骨架固定（宁可短，不许水）：

1. **导语**（80–120 字）：发生了什么 + 为什么今天值得看；
2. **发布的内容**（150–250 字）：能力/版本/可用范围；
3. **关键数据**（条目式）：定价、基准、上下文、限制 —— 只用已校验 facts；
4. **对金风意味着什么**（80–120 字）：延续现有 `us` 的口径，可证伪、不给行动指令；
5. **还有什么不确定**（≤80 字）：原文没说的、只有一方口径的；
6. **来源**（原文链接 + 采集时间）+ `[details="关键事实与引文（可核对）"]` 折叠块：逐条列 claim / quote。

长度目标 600–1000 字（参考站那篇约 10 分钟阅读，内部日报不需要那么长，3–4 分钟更合适）。
实测素材量足够：IT之家那篇 1,785 字正文里就有「100 万 token」「输入 3 美元/输出 15 美元」
「编程智能体指数第一」三组可用事实；官方博文能抽出更多。

### 3.5 降级与回退（必须有，不然会成为新的单点故障）

| 情况 | 行为 |
| --- | --- |
| 正文抽取失败 | 换下一个候选；全失败 → 今天不出焦点，02 退回一句话 |
| 可核对事实 <4 条 | 出一篇「短焦点」（300–500 字，只有导语 + 已校验事实 + 对金风），前端标「简讯」 |
| LLM 两次调用任一失败 | 退回标准模板 + 一句话 summary，round report 记 `focus_failed` |
| 长文校验整体失败 | 不写 632 的 lead 长字段，保留旧值 |

## 4. 数据与前端改动

### 4.1 `feed.lead` 新增字段（向后兼容，旧字段全保留）

```json
"lead": {
  "title": "…", "summary": "导语（≤160 字）", "us": "对金风一句（≤50 字）",
  "cred": "y", "credLabel": "双重验证", "sources": [{"label": "…", "url": "…"}],
  "url": "https://aicopilot…/t/1234",          // 阅读全文 → 焦点话题
  "points": ["100 万 token 窗口", "输入 3 美元/百万 token", "编程智能体指数第一"],
  "kind": "focus",                              // focus | brief（简讯）
  "reading_minutes": 3,
  "claims": [{"text": "…", "quote": "…", "source": "…"}]   // 机器可读，供后续归档/RSS
}
```

底座帖只多约 400–600 字符（导语 + 3 条要点 + 链接），不触碰 28,000 预算，不挤 radar。

### 4.2 前端（主题组件 v0.4.8，**需要人工打补丁**）

主题写 API 仍是 404（`docs/前端组件待应用补丁.md` 已记录），所以这一环只能手动贴。
改动很小，只动 `components/ai-pulse-home.gjs` 的 `ap-lead` 块（当前 line 539–553）与 `ai-pulse-feed.js` 的 `normCard`：

- `<h2>` 标题后加一行 `{{lead.summary}}`（导语）；
- 加 `\{\{#each lead.points\}\}` 的 3 条要点列表（每条 ≤24 字，CSS 用现有 `ap-lead__body` 字号）；
- 底部加 `阅读全文 →`（`lead.url`），保留 cred chip 与来源链接；
- `LIMITS` 里给 lead 单独开一个 `leadPoints: 24` / `leadDeck: 160`，**不动** `summary: 320`（radar 卡片还在用）。

**不改前端的降级路径**：`lead.summary` 直接写满 320 字的导语、`title` 链到焦点话题。
观感是「一段长一点的摘要 + 可点进去」，仍不是分节文章，但当天就能用。

## 5. 方案选项与推荐

| 方案 | 内容 | 工作量 | 观感 |
| --- | --- | --- | --- |
| A 最小 | 焦点独立成长文话题（论坛里能读全文），首页 02 不改前端：标题链过去 + summary 写满 320 字 | 0.5 天 | 首页仍像一句半，点进去才是文章 |
| **B 推荐** | A + `feed.lead` 扩展 + 前端 v0.4.8 补丁（标题/导语/3 要点/阅读全文） | 1 天（其中前端 30 分钟人工） | 对标参考站首页入口卡 |
| C 完整 | B + 焦点归档页（今日/本周）+ RSS / `brief.json` 对外接口 | 2–3 天 | 等于自建 ai-pulse-lab，需额外托管，**不建议现在做** |

推荐 **B**。C 的价值主要在对外分发，而我们的受众在论坛里。

## 6. 成本与风险

- **耗时**：+1 次抓取（≤3 秒）+ 2 次模型调用（实测单次 1.7 秒，最坏 45 秒超时）+ 发帖 16 秒 ≈ **+25–60 秒**，
  轮预算 1,200 秒完全够；调用数从 38 次升到 40 次，不影响限速。
- **幻觉**：靠 §3.3 的逐字引文校验兜住；校验不过就降级，不会「写得很漂亮但事实错」。
- **抓取失败率**：企业网对外站点不稳定（Hugging Face 已连续 9 轮失败），所以焦点选题规则里
  把「抽取成功」作为硬条件，失败就顺位换题，不硬写。
- **重复**：`event_key` 7 天内只做一次焦点；一天固定一篇，12/16 轮不换题。
- **前端手工环节**：唯一无法自动上线的部分；建议把补丁写进 `docs/前端组件待应用补丁.md` 的同一份清单里。

## 7. 需要你拍板的 3 件事

1. **频率**：一天一篇（08:00 定稿，推荐）还是每轮一篇？
2. **01 让位**：焦点是否从 01 简报里移出（避免同页重复），还是两块都保留？
3. **前端补丁**：接受「我出补丁、你手动贴到主题组件 v0.4.8」，还是先用 A 方案的降级路径跑起来？

## 8. 验收标准（V1 上线后按这个验）

- 焦点正文 600–1000 字、≥5 段、claims ≥4 条且 100% 通过逐字引文校验；
- 抽取失败降级比例 <20%（连续 5 天统计）；
- 首页 02 卡片高度不超过当前「焦点 + 导语 + 对金风」两倍（不撑破版式）；
- 632 正文字符数增长 <1,000（预算不破）；
- 一轮总耗时增长 <90 秒。

## 9.2 和原方案的三处不同

1. **一天一篇 → 每轮最多一篇，且「没有新事件就不换」**（你选的口径）。实现上就是选题只从
   **本轮新信号**里挑；本轮挑不出来就不动 02，上一轮的焦点留在页面上。好处是 08/12/16
   任一轮出大事都能当天开长文；代价是一天可能出现两篇长文（待观测）。
2. **正文抽取用 bs4 启发式，没引入 trafilatura/lxml**。venv 里没有这两个包、内网 pip 不可靠，
   代价是抽出来的正文偶尔带一句导航残留，收益是零新增依赖。
3. **多了一条「换来源重抓」**。实现时发现**新华网正文是 JS 渲染的**——HTML 里一个 p 标签都没有，
   抓到的是导航栏标题。于是 `focus.candidate_urls()` 会按来源顺序逐个试，抓到正文的那条来源
   自动排到「来源」首位。第一版 demo（话题 866）就是靠这条救回来的：新华网抓不到 → 换到
   能源局官网静态原文（2,752 字）。

   **再加一层「站点可抓性」记忆**：每轮把「哪个站点抓得到正文」记进 state 表（focus_host_stats），
   选题时**可抓性排在一手/相关度之前**。理由是焦点是硬要求——抓不到正文就出不了稿；不这么排，
   每轮都会在同一批 JS 渲染页上白花 3 次超时，最终变成「本轮不出焦点」。这层记忆是自学习的结果，
   不是人工白名单：站点改版后抓到一次，排序就恢复正常。

## 9.3 质量闸门（防「写得漂亮但事实错」）

- `verify_claims()`：引文必须能在正文里**逐字**找到（NFKC 归一 + 去空白 + 小写后比对），
  数字同理，对不上的直接删。话题 866 实测：模型给 7 条、7 条全过；只抓到导航的候选只过 1 条，
  直接被判「事实不足」不出稿。
- `claims_min: 4` → 不足 4 条出「简讯版」（正文里明写「本篇为简讯」）；
  `degraded_claims_min: 2` → 不足 2 条本轮不出稿。
- 成稿只拿到「已核对事实 + 原文引文 + 可用数字」，提示词禁止引入新事实、禁止行动建议。
- 发帖失败（429 / 读回不一致）**不写** `focus_history` —— 否则事件键被占住，这个事件 7 天内再也做不了焦点。

## 9.5 上线后要盯的三件事

1. **JS 渲染页占比**。新华网这种站点抓不到正文，焦点会向「静态官网」倾斜。若连续几天焦点全是
   官网稿，说明媒体稿基本不可用，需要评估渲染服务或站内镜像——那是新增依赖，先观测一周再决定。
2. **每轮一篇的实际频率**。看 `collector status` 里的「焦点 N 字/M 条事实」与 `focus_skipped` 原因：
   「事实不足」占比高说明 claims_min 或提示词要调；「本轮没有新的焦点级事件」占多数是正常的。
3. **632 预算**。焦点摘要从 ~120 字涨到 ≤320 字，`_fit_feed` 已把 radar 从 36 压到 35。若某天
   同时出现「焦点 + 大量一手新稿」可能压到 33 条以下；届时优先降 `feed.window_hours`，不动 POST_CHAR_BUDGET。
## 9.6 两次 dry-run 的对比（自学习是真的在工作）

`run --dry-run`（真实抓取 + 真实模型，论坛是模拟的）连跑两轮，节点如下：

| 轮次 | 焦点结果 | 说明 |
| --- | --- | --- |
| 第 1 轮 12:51 | **本轮不出焦点** | 3 条候选全部抓不到正文：新华网 142 字（JS 渲染）、openai.com 403、openai.com 403 |
| 第 2 轮 12:56 | **出稿 519 字 / 5 条事实** | 选题自动跳过了上轮抓不到的站点，落到「中新 AI 治理交流会议」，整轮 251 秒 |

第 2 轮的首页结果（dry-run 的底座帖）：`kind=focus`、链接指向新话题、摘要 122 字，01 三条里不含焦点。
这就是 `focus_host_stats` 的价值：不是靠人写白名单，而是让系统自己记住哪个站点抓得到正文。

顺带一提，第 1 轮那三条失败也说明「事实闸门」是真的在拦：新华网只抓到导航栏，
模型从导航里硬挤出的 1 条事实达不到 `degraded_claims_min`，于是整条被丢掉，没有变成一篇胡编的长文。
